# V0.2 Ticket-Driven Review Loop (design candidate)

## Purpose
Codex is an **independent reviewer**, not a magic assurance of total correctness. Require it to inspect all relevant code paths and **report every substantiated finding in one comprehensive sweep**, without stopping at the first issue. Any discovered defect becomes a durable ticket, and every existing ticket remains tracked until verified fixed or explicitly waived with owner authorization. A model-generated PASS by itself is not release approval.

## Workflow: 3 normal, 5 absolute maximum **per explicitly authorized new campaign**
1. Pin integrated repo HEAD; capture current main merge base and a clean worktree. No production DB, no merges.
2. Run deterministic suites / PostgreSQL isolation test / typecheck / build / browser gates in a TEST environment. Record PASS/FAIL/NOT_RUN with commands.
3. Run standalone Sol reviewer in **ticket mode** (set SOL_REVIEW_TICKET_MODE=1). The response must enumerate all high-confidence findings, not just five arbitrary samples, and append valid ticket JSON. It must explicitly inspect previous open tickets and mark each VERIFIED_FIXED, OPEN, REGRESSED, or DISPUTED with evidence.
4. If review FAIL, normalize/deduplicate tickets by root cause, path, and behavior; preserve original ticket IDs. Assign disjoint file ownership in cbds via current installed, verified commands. Exact changes and test cases go to AGY workers.
5. Integrate only accepted cbds reports and commits; prevent owner overlap. Run all test/build gates again. Ensure integrated SHA changes before another full review.
6. Repeat until all nonwaived blocking issues are independently verified fixed and release gates pass. Default 3 review rounds, configurable up to 5 **new reviewed SHAs per campaign**. A prior already-failed review can be imported as the starting backlog without consuming a new review. Never erase past reviews or open ticket statuses. Count distinct reviewed SHAs, **not** shell retries.
7. On PASS, re-verify exact SHA and all gates; call it REVIEW_PASS_PENDING_RELEASE_GATES until the owner signs off. Never auto-merge.
8. On fifth FAIL, unresolved P0/P1, flaky tests, environment BLOCKED, incomplete reports, repeated SHA, conflicting state or budget limit: STOP and output comprehensive remaining-ticket report for the maintainer; never lie or retry forever.

## Issue ticket contract
A useful ticket must contain:
- Stable ID, severity P0/P1/P2/P3, affected domain and exact relative path:line(s).
- Observed behavior and impact, explicit reproduction with inputs and expected vs actual results.
- Root-cause explanation and relevant call sites (or say uncertain, never fabricate).
- Proposed repair *strategy* and alternative constraints; avoid implementing changes in a read-only review.
- Precise acceptance criteria and regression tests, ideally SQL-backed concurrency tests.
- User/data/financial invariants, migration and compatibility implications.
- Existing-ticket status (OPEN / REGRESSED / VERIFIED_FIXED / DISPUTED) with proof.
- Risks or unresolved product decisions; no silently chosen behavior.
- Exactly which tests really ran and which were NOT_RUN.

Machine representation: exactly one fenced JSON packet following the human report, validated by scripts/validate-sol-tickets.py. Missing/invalid packet makes the reviewer result BLOCKED in ticket mode, not PASS.

## Review coverage checklist for NutriSnap
- Account/transaction authorization and tenant isolation.
- Exact Decimal money mathematics, balance conservation, repayment and reversal.
- Loan, obligation and credit-card statement lifecycle integrity and history.
- Concurrent commands and idempotency (two identical submissions; two different commands).
- Calendar-month, timezone, due-day, explicit null/absent value semantics.
- Reminder delivery/claim status: PENDING, SENT, SNOOZED, ACKNOWLEDGED.
- UI form -> server action -> service -> Prisma path and unauthorized bypass.
- Postgres-backed tests, security, typecheck, build, browser/runtime gates, and current-main compatibility.

A completeness statement means *all named areas were examined* and exclusions identified; it never proves there are zero hidden bugs.

## Orchestration state/stop policy
- One active cbds coordinator/run, one owner per source file.
- Limit new independent reviewer calls per cycle to **one**; shell/protocol failure is BLOCKED, never a new repair round.
- New repair round requires new integrated Git SHA and valid worker reports + test evidence.
- Do not auto-reopen closed tasks without actual regression. Don't rewrite successful tests to hide failures.
- The maximum is an anti-loop **stop condition**. Prompting "keep going until PASS" without a cap, independent tests and ticket persistence encourages confirmation bias.
- No broader scope creep when a reviewer discovers unrelated P3 style issues; preserve such tickets separately.
- Any model, memory, execution, worker or cbds budget limit stops and records BLOCKED.
- Worker commits and reviewer reports survive session crashes; rehydrate state instead of redispatching completed work.
- GitHub ticket publication is allowed only to an intended repo/branch with proper access; never create duplicate issues every round.

## Release rule
Approval = independent Sol **review PASS on exact final SHA** + every required non-model software gate PASS + all previously open blocking tickets VERIFIED_FIXED + human sign-off. If any gate NOT_RUN or FAIL, release status is HOLD regardless of review label.
