## Proposed amendment to W02 contract — review and incorporate, not code

**A. Numeric entry / bounds:** Add an accessible exact whole-milliliter input for at least 330 ml while retaining the existing slider/presets and their behavior. A numeric amount should be validated consistently with `validateHydrationAmount` (1–10,000 integer ml); do not silently truncate, round 330 to 300/350, or widen the slider without reason. Define whether numeric editing beyond the slider visual range is acceptable or should be blocked in the UI; if existing contract already specifies an equivalent approach, preserve it. Scope the actual UX implementation to the smallest change.

**B. Reload / Today:** After saving (and editing) exactly 330 ml, reloading the Water screen must show the persisted entry and correct sum. Visiting Today (including return navigation and a fresh page load) must show matching same-day totals for the authenticated user, respecting their configured date/timezone. Do not add a second hydration state engine, polling service or scheduler; only remedy a reproducible stale view if the tests demonstrate it.

**C. Authorization / isolation:** Require tests that user A can create/read/update own hydration logs and user B cannot spoof A for create/read or edit A's log. Use a disposable/isolated database or an existing fully isolated test harness. Mark tests NOT_RUN until executed. No production credentials or owner data.

**D. Small regression set:** Preserve quick-add 250/500/750, existing slider increments, other drink types, edit flow and daily total calculation. Negative values, fractional values, NaN/non-finite and out-of-range values must be rejected server-side; avoid overextending W02 into W03–W09 of issue #171.
